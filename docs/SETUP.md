# Deliberate owner-only setup

1. Complete the questions in AGENTS.md. Category labels and eight UI frames are currently Japanese; adapting vocabulary is a tested code change, not an implemented multilingual setting. Nonempty merchant_rules are not supported and must be rejected. No personal merchant rules are seeded.
2. Copy `config/profile.example.json` to an ignored local profile. Validate with `node tools/check-config.cjs <path>`. Example values must fail. Map fields to Script Properties: OWNER_EMAIL, LEDGER_SPREADSHEET_ID, LEDGER_MODE, MAIL_INBOX_FOLDER_ID, MAIL_INBOX_PARENT_ID, MAILBOX_ALIASES (JSON array), LEDGER_ACCOUNTS_JSON (JSON array). No author destination fallback exists.
3. Run the synthetic suite and `node webapp/tools/package.cjs`. Review generated sources and `appsscript.json`. Requested Google scopes include Sheets, user identity and Drive read-only; Drive consent itself covers more than the fixed inbox. Explain this to the user. Gmail retrieval belongs to the user's connector; GAS does not request full Gmail access.
4. Only after user authorization, create a separate empty demo Sheet/project; enable the Sheets advanced service, add generated GAS files and properties. Add `webapp/setup-only/TemporarySetup.gs` temporarily to expose initialization, then remove it before deployment. Initialization rejects existing/nonempty ledgers, checks that the Sheet is owned by the configured owner with PRIVATE sharing and no other editors/viewers, and stops if that check cannot be completed. It validates the complete initial state before writing. This is an initialization check, not continuous Sheet ACL monitoring. The user completes Google consent. Deploy as self, access self only. Separately verify the spreadsheet and folders are owned by the configured owner and have no other users, group, domain or public access. Owner-only web-app access does not make the underlying files private. Do not publish an anonymous endpoint.
5. Verify synthetic save/read/retry/conflict/undo and mobile layout in that demo. A separate empty personal Sheet/project is required; never turn demo state into personal by editing mode. Initial accounts come from the user's config; demo transactions are synthetic and demo asset balances start empty so fixed fixture accounts cannot conflict with custom account names. Back up source and state before updates.
6. Daily transport setup is a separate approval and adapter-validation step. The fixed worker's public CLI is included for offline validation and confirmation, but no general connector or scheduler is shipped. Demonstrate the adapter contract with synthetic data in the user's isolated environment before enabling any real intake. There is no one-click installer, connector login or schedule creator.
7. For later releases: immutable build hash, backward-compatible schema/capability, full-table backup, safe HEAD update ordering and old exchange compatibility are required. Verify deployment and HEAD processing separately, then bootstrap with no financial mutations, canary and readback. Never regard UI deployment version alone as runtime capability proof.
